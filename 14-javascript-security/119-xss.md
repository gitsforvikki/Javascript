# Lesson 119 — XSS Fundamentals

Cross-Site Scripting, or **XSS**, happens when untrusted data is treated as executable content in a web page.

The core idea is:

> Data that should be displayed becomes code that the browser executes.

XSS can let an attacker act inside the victim's browser with the permissions of your site.

---

## 1. Basic Mental Model

```text
untrusted input
↓
unsafe insertion into page
↓
browser interprets it as HTML/JavaScript
↓
attacker-controlled code executes
```

The bug is not merely:

```text
"bad string"
```

The real bug is:

```text
untrusted data
+
unsafe execution context
```

---

## 2. Why XSS Is Dangerous

Attacker-controlled JavaScript may be able to:

- read page data
- make authenticated requests
- modify the UI
- steal JavaScript-readable tokens
- impersonate user actions
- capture form input
- redirect users
- abuse application APIs

Impact depends on what the page and session allow.

---

## 3. Stored XSS

Stored XSS happens when malicious content is saved by the application and later rendered unsafely.

Flow:

```text
attacker submits content
↓
server stores it
↓
another user loads page
↓
stored content is inserted unsafely
↓
code executes
```

Examples of storage locations:

- comments
- profiles
- support tickets
- product descriptions
- admin notes

---

## 4. Reflected XSS

Reflected XSS occurs when request-controlled data is immediately included in a response or page without safe handling.

Flow:

```text
URL/query input
↓
application reflects value
↓
browser renders unsafe result
↓
script executes
```

The malicious value is not necessarily stored permanently.

---

## 5. DOM-Based XSS

DOM XSS happens when client-side JavaScript reads attacker-controlled data and sends it into an unsafe DOM sink.

Example sources:

- URL parameters
- location hash
- localStorage
- postMessage
- API response
- form input

Unsafe sink example:

```js
element.innerHTML =
  untrustedValue;
```

---

## 6. Source and Sink Mental Model

Security reviews often think in terms of:

```text
SOURCE
↓
untrusted data enters

TRANSFORMATION
↓
application manipulates it

SINK
↓
dangerous browser API interprets it
```

Example:

```text
location.search
↓
URLSearchParams
↓
innerHTML
```

---

## 7. Safe Text Rendering

If you want plain text:

```js
element.textContent =
  userInput;
```

This tells the browser:

> Treat this as text, not HTML.

That is fundamentally safer than parsing the string as markup.

---

## 8. React Escaping

React normally escapes values rendered inside JSX:

```jsx
<p>
  {userInput}
</p>
```

This helps prevent raw HTML execution.

But React can still become unsafe if you deliberately bypass escaping.

---

## 9. dangerouslySetInnerHTML

React provides:

```jsx
<div
  dangerouslySetInnerHTML={{
    __html:
      htmlContent,
  }}
/>
```

The name is intentionally explicit.

If `htmlContent` contains untrusted HTML, XSS may become possible.

Use only with trusted or properly sanitized content.

---

## 10. Escaping vs Sanitizing

These are different.

### Escaping

Convert special characters so they are treated as text.

Example conceptually:

```text
<
↓
&lt;
```

### Sanitizing

Allow some HTML but remove dangerous content.

Example:

```text
allow:
<p>
<strong>

remove:
dangerous attributes/elements/URLs
```

---

## 11. Context Matters

Security handling depends on where data is inserted.

Different contexts include:

- HTML text
- HTML attribute
- URL
- JavaScript
- CSS

A defense correct for one context may be wrong for another.

Avoid inventing your own generic "escapeEverything()" helper.

---

## 12. Sanitization Libraries

If your product must render user-controlled HTML, use a well-maintained sanitizer designed for that purpose.

Do not rely on simple regex replacement.

HTML parsing rules are too complex for homemade regex sanitization.

---

## 13. Content Security Policy

Content Security Policy, or CSP, can reduce XSS impact.

CSP can restrict:

- script sources
- inline scripts
- object/embed content
- framing
- other resource execution

CSP is defense-in-depth.

It does not replace safe rendering.

---

## 14. Why Inline Script Restrictions Help

A strong CSP can make some injected scripts harder to execute.

But attackers may still exploit allowed scripts or unsafe DOM APIs.

So think:

```text
safe coding
+
sanitization when needed
+
CSP
```

not:

```text
CSP only
```

---

## 15. HttpOnly Cookie Connection

If a session cookie uses:

```text
HttpOnly
```

attacker JavaScript cannot directly read it through:

```js
document.cookie
```

But XSS may still let malicious JavaScript send authenticated requests from the page.

So HttpOnly reduces some impact but does not make XSS harmless.

---

## 16. localStorage Risk

If authentication data is stored in:

```js
localStorage
```

successful XSS can typically read it.

This is one reason sensitive long-lived credentials should not be casually stored there.

---

## 17. URL Handling

Be careful with attacker-controlled URLs.

Example risk:

```js
link.href =
  userProvidedUrl;
```

Validate allowed schemes and destinations when security matters.

Do not assume every string that "looks like a URL" is safe.

---

## 18. postMessage Connection

Cross-window messaging can introduce untrusted input.

Always validate:

- `event.origin`
- message structure
- expected data types

before using message data in the DOM.

---

## 19. Trusted Types

Trusted Types is a browser security mechanism that can help prevent DOM XSS by restricting dangerous sink assignments to vetted trusted values.

It is especially useful in large applications with strict CSP policies.

This is an advanced defense-in-depth tool.

---

## 20. XSS Prevention Checklist

```text
1. Treat external data as untrusted
2. Prefer textContent / JSX escaping
3. Avoid raw HTML sinks
4. Sanitize required HTML
5. Validate URLs
6. Use CSP
7. Protect cookies with HttpOnly/Secure where appropriate
8. Review third-party scripts
9. Avoid dangerous dynamic code APIs
```

---

## 21. Next.js Connection

In Next.js:

- JSX values are escaped by default
- Server Components do not magically make unsafe HTML safe
- `dangerouslySetInnerHTML` still requires trusted/sanitized content
- secrets should stay server-side
- CSP can be configured through headers

Security depends on data flow, not just framework choice.

---

## 22. Common Mistakes

### Mistake 1

Thinking React completely prevents XSS.

### Mistake 2

Sanitizing with regex.

### Mistake 3

Trusting API data just because it came from your backend.

### Mistake 4

Assuming HttpOnly makes XSS unimportant.

### Mistake 5

Using innerHTML for convenience when textContent is enough.

---

## Interview Questions

### What is XSS?

A vulnerability where attacker-controlled data is executed as active content in another user's browser.

### Stored vs reflected vs DOM XSS?

Stored is persisted, reflected comes from a request and is immediately reflected, and DOM XSS happens through unsafe client-side DOM processing.

### Escaping vs sanitizing?

Escaping renders data as text; sanitizing allows controlled HTML while removing unsafe content.

---

## Key Takeaways

- XSS is an execution-context problem.
- Untrusted data must not reach dangerous sinks unsafely.
- Prefer text rendering over HTML parsing.
- React escaping helps, but unsafe escape hatches still exist.
- Sanitization is required when rendering untrusted HTML.
- CSP and HttpOnly are defense-in-depth, not primary fixes.
